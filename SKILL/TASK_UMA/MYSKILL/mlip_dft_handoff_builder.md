# MLIP DFT Handoff Builder

## Purpose

Create the final downstream handoff summary for DFT/VASP input generation after MLIP relaxation.

## Position in MESA Pipeline

This protocol runs at the end of `TASK_MLIP_DFT_HANDOFF`. Its output is consumed by the downstream VASP input generation task.

## Inputs

Inputs are the configured UMA settings, `optimized/POSCAR`, runner metadata, and the MLIP reliability report.

For Codex agent execution, this protocol also defines how to decide missing UMA execution settings before the controller is run. Those decisions must be written into the controller input JSON under `mlip_settings` and `relaxation_settings`.

## Outputs

The protocol writes `results/dft_handoff_summary.json`. The handoff summary includes the optimized POSCAR path, model, task, relaxation mode, energy, force metadata, convergence state, reliability status, and a downstream recommendation.

## Algorithm

1. Confirm whether `optimized/POSCAR` exists.
2. Read available single-point and relaxation metadata.
3. Include UMA model, task, device, relax type, force threshold, and step limit.
4. Include reliability status and summary.
5. Recommend `generate_vasp_inputs` only when `optimized/POSCAR` exists and reliability status is `pass`.
6. Record that this task does not create VASP input folders or POTCAR contents.

## UMA Settings Decision Policy

When explicit MLIP settings are absent and Codex receives a POSCAR, Codex must inspect the structure and runtime environment before running the controller. Codex should use scientific judgment to choose suitable UMA execution settings, then serialize those choices into the controller input JSON.

Codex must decide:

- `mlip_settings.model`
- `mlip_settings.task`
- `mlip_settings.device`
- `relaxation_settings.relax_type`
- `relaxation_settings.fmax`
- `relaxation_settings.steps`

Codex should base the decision on the POSCAR contents, any upstream scientific context, the intended execution mode, and the available runtime environment. It should record the chosen values and the reasoning in its response or run notes before executing the controller.

If Codex has no better scientific or runtime reason to override them, the fallback settings are `model=uma-s-1p2`, `task=omat`, `device=cuda`, `relax_type=geometry`, `fmax=0.05`, and `steps=300`. If the decision is uncertain, Codex should choose an executable setting, record the uncertainty, and rely on the generated reliability and handoff summaries to decide whether downstream DFT input generation is ready.

## Dependencies

This protocol uses the Python standard library and JSON files generated by this TASK.

## Failure Modes

The handoff summary returns `not_ready` when `optimized/POSCAR` is missing, runner outputs are unavailable, or reliability does not pass.

## Example

```json
{
  "status": "ready",
  "downstream_artifact": "optimized/POSCAR",
  "recommended_next_skill": "generate_vasp_inputs",
  "mlip": {
    "model": "uma-s-1p2",
    "task": "omat",
    "relax_type": "geometry",
    "reliability_status": "pass"
  }
}
```

## Validation

After a successful relaxation, verify that `optimized/POSCAR` exists and the handoff summary recommends `generate_vasp_inputs`.

## Limitations

The builder does not generate `INCAR`, `KPOINTS`, `POTCAR`, pseudopotential files, or VASP job folders.
